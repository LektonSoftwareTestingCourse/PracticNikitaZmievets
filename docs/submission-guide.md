# Submission Guide — курс тестирования ПО, ИТМО

> **Модель сдачи:** каждый студент работает в **своём отдельном репозитории** внутри организации — `Practic{Имя}{Фамилия}` (например, `PracticBogdanKozlov`). Репозиторий студента изолирован от эталонного `Practic`, поэтому работы студентов никогда не попадают в `main` эталона.
>
> **PR не используется.** Сдача — через **Issue в эталонном репозитории** `Practic` с label `practice-N`. Студент сам вставляет в Issue ссылку на свой репозиторий и на конкретный прогон CI.

## Общий workflow

1. **Получить свой репозиторий** `Practic{Имя}{Фамилия}` (его создаёт куратор и выдаёт вам доступ на запись).
2. **Склонировать свой репозиторий**, а не эталонный:
   ```bash
   git clone https://github.com/<org>/Practic<Имя><Фамилия>.git
   cd Practic<Имя><Фамилия>
   ```
3. **Создать ветку** `practice-{N}` от `main` (например, `practice-2`). Для простоты допускается работать прямо в `main`.
4. **Выполнить задание**, разместив артефакты по путям согласно таблице ниже.
5. **Запушить ветку** — лёгкий CI в вашем репозитории запустится автоматически (линтеры, компиляция, unit-тесты).
6. **Запустить тяжёлую проверку вручную** (для практик 1, 5, 6): вкладка Actions → workflow «Practice Run (heavy checks)» → «Run workflow» → выбрать номер практики. Эта проверка билдит docker-образы и гоняет smoke/e2e/load-smoke.
7. **Открыть свой Actions-прогон** в вкладке Actions и убедиться, что он зелёный.
8. **Создать Issue в эталонном репозитории** `Practic` с заголовком «Практика N — Фамилия», label `practice-N`. В теле Issue указать:
   - **Ссылку на свой репозиторий** (`https://github.com/<org>/Practic<Имя><Фамилия>`);
   - **Ссылку на ветку** и **ссылку на конкретный Actions run** (кнопка «…» → «Copy link» на странице прогона);
   - Путь к артефакту;
   - **Полное содержимое артефакта** (для LLM-проверки текстовых практик).
9. Преподаватель проверяет: переходит по ссылке на Actions run (для кодовых практик) + прогоняет LLM-проверку (для текстовых).
10. Результат — в комментарии к Issue.

## Синхронизация с эталонным репозиторием

Ваш репозиторий создаётся как копия эталонного `Practic`. Если куратор обновил эталон (поправил ТЗ, CI, docker-compose), подтяните изменения к себе:

```bash
# один раз добавить эталон как upstream
git remote add upstream https://github.com/<org>/Practic.git

# подтянуть обновления
git fetch upstream
git checkout main
git merge upstream/main
git push origin main
```

> Держите свои артефакты в отдельных файлах/ветках, чтобы синхронизация не порождала конфликты. Ваши студенческие работы в эталон не мёржатся.

## CI — два уровня проверок

### Автоматические (лёгкие), на каждый push

Лёгкий пайплайн [`ci.yml`](../.github/workflows/ci.yml) гоняется **автоматически** на каждый push и не требует секретов.

| Джоба | Что делает | Какие практики |
|---|---|---|
| `base-lint` | pre-commit хуки (YAML, JSON, пробелы, trailing whitespace) | Все |
| `java-services` | Сборка + линтер (checkstyle) + unit-тесты (matrix по 7 сервисам) | 3, 4 |
| `frontend-dashboard` | ESLint + сборка React-приложения | Все |

### Ручные (тяжёлые), через «Run workflow»

Тяжёлый пайплайн [`practice-run.yml`](../.github/workflows/practice-run.yml) билдит docker-образы и поднимает все сервисы, поэтому **запускается вручную** — только когда вы готовы сдавать:

> **Actions → Practice Run (heavy checks) → Run workflow → выбрать номер практики.**

| Джоба | Что делает | Практика |
|---|---|---|
| `smoke-tests` | `docker compose up -d` + health-check всех сервисов | 1 |
| `e2e-tests` | E2E-тесты из модуля `e2e-tests` | 5 |
| `load-smoke` | Запуск нагрузочного сценария студента (см. ниже) | 6 |

## `load-smoke` — как работает

**Нагрузочное тестирование выполняется локально.** CI проверяет только работоспособность скрипта (smoke-уровень).

### Локально (студент)

Студент создаёт скрипт [`scripts/load-smoke.sh`](scripts/load-smoke.sh) в своём репозитории и запускает его на своей машине:

1. `docker compose up -d`
2. Генерирует тестовые карты (`POST /api/cards/generate`)
3. Запускает `scripts/load-smoke.sh` с `LOAD_COUNT=500` (или своим значением)
4. Собирает метрики (p50/p95/p99, throughput, error rate, avg response time)
5. Описывает результаты локального прогона в [`docs/practice-6/test-summary.md`](docs/practice-6/)

Студент **сам определяет**: сценарий, количество транзакций, собираемые метрики.

### В CI (автопроверка)

CI-джоба `load-smoke` делает **smoke-проверку** скрипта:

1. Поднимает docker compose
2. Генерирует тестовые карты
3. Запускает `scripts/load-smoke.sh` с `LOAD_COUNT=10` (smoke-уровень — только проверка, что скрипт не сломан)
4. Если скрипт завершился без ошибок — ✅ OK
5. Если скрипт отсутствует — CI выводит предупреждение, но не фейлит билд

> **Почему не 500 в CI:** GitHub Actions раннеры (2 ядра, 7 GB RAM) не обеспечивают стабильных метрик для нагрузочного тестирования. Реальные замеры — только локально.

## Как работает LLM-проверка (промежуточный вариант)

> **Текущий статус:** промежуточный шаг перед полной автоматизацией через GitHub Actions + LLM API.

1. Студент копирует **полное содержимое артефакта** в тело Issue
2. Преподаватель копирует Issue-текст + промпт (предоставляется преподавателем) → отправляет в LLM (ChatGPT / DeepSeek / Claude)
3. LLM возвращает JSON с оценкой по рубрике
4. Преподаватель копирует JSON-результат в комментарий к Issue
5. Если `needs_manual_review: true` — преподаватель проверяет вручную и добавляет label `needs-review`

## Часто задаваемые вопросы

### Почему не PR?

Студенческие тесты и артефакты не предназначены для слияния в `main` эталонного репозитория. `main` эталона содержит production-код СМП (симулятора процессингового центра). Каждый студент работает в своём изолированном репозитории, а Issue + label обеспечивает прослеживаемость сдачи без засорения эталонного репозитория.

### Почему тяжёлые проверки запускаются вручную?

Docker-сборка (~11 образов) на каждый push быстро расходует бесплатную квоту Actions-минут. Поэтому на каждый push автоматически гоняются только быстрые проверки (линтеры, компиляция, unit-тесты), а тяжёлые smoke/e2e/load-smoke запускаются вручную один раз в момент сдачи.

### Почему не автоматический вердикт по CI?

Прогоны CI живут в **ваших** репозиториях, а Issue создаётся в **эталонном**. Читать Actions чужого репозитория автоматически сложно и требует токенов, поэтому вместо автоматики вы сами вставляете ссылку на свой Actions run, а преподаватель проверяет её одним кликом.

### Как узнать, что CI прошёл?

После пуша откройте вкладку **Actions в своём репозитории** — вы увидите статус пайплайна для вашей ветки. Зелёный — всё хорошо, красный — нужно поправить ошибки и запушить снова. Эту ссылку на зелёный прогон вы и прикладываете в Issue.

### Где смотреть результаты LLM-проверки?

Преподаватель публикует JSON-результат в комментарии к вашему Issue. Там же будет указано, нужно ли что-то доработать.
