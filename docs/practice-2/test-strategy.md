# Тестовая стратегия СМП

## 1. Цель тестирования

Цель — подтвердить, что СМП корректно проводит карточную транзакцию по цепочке Terminal / Merchant Simulator → Gateway → Switch → Authorization → Card Management → RabbitMQ → Transaction Logger → Web Dashboard. Система должна принять верное решение `APPROVED` или `DECLINED` с правильным `responseCode` (00, 05, 14, 51, 54, 61, 96), один раз и на правильную сумму изменить баланс и счётчики лимитов и не потерять транзакцию при асинхронной доставке в журнал.

Главные характеристики качества на текущем этапе:

- функциональная корректность авторизации, управления картами и маршрутизации;
- целостность денег: нет двойного резервирования, списания при отказе и отрицательного баланса;
- корректность REST-контрактов и кодов ответа;
- надёжность синхронных (HTTP) и асинхронных (RabbitMQ) взаимодействий;
- наблюдаемость: health-check, логи, диагностируемые ошибки;
- безопасность тестовых данных: только синтетические PAN, без персональных данных.

Измеримые цели:

- каждое требование ядра (ТЗ-04, ТЗ-05) трассировано хотя бы на один тест-кейс;
- каждый код отказа проверен хотя бы одним тестом;
- ни одна транзакция не получает `APPROVED` без резервирования средств и публикации в очередь `transaction-log`;
- при недоступности Card Management, Bin Lookup или RabbitMQ поведение соответствует ТЗ: отказ с нужным кодом или fallback.

Критичными считаются риски, ведущие к неверному `APPROVED`, потере или двойному изменению средств, потере записи о транзакции или неуникальному RRN.

## 2. Уровни проверок

| Уровень | Что проверяется | Инструменты | Модуль курса |
|---|---|---|---|
| Статический | Полнота и непротиворечивость ТЗ, api-spec и OpenAPI; тест-дизайн до кода | Ревью, PICT | 2 |
| Smoke | Все сервисы поднимаются, health-check 200, проходит одна транзакция | `scripts/smoke-test.sh` | 1, перед каждым прогоном |
| Unit | Бизнес-правила в изоляции: порядок проверок и лимиты, Луна и генератор, валидация Gateway, маршрутизация Switch | JUnit 5, Mockito, параметризация | 3 |
| API | REST-контракты, статус-коды, decline-коды | REST Assured, OpenAPI | 4 |
| Интеграционный | Сервис с реальной БД и брокером: `limit_usage`, outbox → Notification, Switch → RabbitMQ → Logger | Testcontainers | 4 |
| E2E | Сквозные сценарии через Gateway: покупка, отказы, reversal, дашборд | `services/e2e-tests` | 5 |
| Нефункциональный | p50/p95/p99, throughput, error rate, гонки резервирования, отказы зависимостей | `scripts/load-smoke.sh`, остановка контейнеров | 6 |

Распределение следует пирамиде тестирования. Основная масса проверок бизнес-правил выполняется на unit- и API-уровнях: они быстрые, стабильные и точно указывают на место дефекта. На E2E выносится только критический путь: сквозные тесты дороги и нестабильны из-за eventual consistency между Switch и Logger.

## 3. Область тестирования и обоснование исключений

| Слой | Сервисы | Глубина | Обоснование |
|---|---|---|---|
| Ядро | Authorization, Card Management | Классы эквивалентности, границы, pairwise; unit + API + интеграция | Финансовое решение и изменение баланса, наибольшая плотность правил |
| Транзакционный контур | Gateway, Switch, Transaction Logger, Bin Lookup | API, интеграция, чек-листы, E2E критического пути | Валидация, маршрутизация, гарантии доставки, идемпотентность журнала |
| Периферия | Terminal / Merchant Simulator, Notification Service, Web Dashboard | Чек-листы дымового тестирования и критического пути | Генерируют нагрузку или отображают данные, решение по транзакции не меняют |

Осознанно исключено:

| Исключение | Основание |
|---|---|
| Реальные платёжные сети, бинарный ISO 8583, внешние BIN | СМП эмулирует обмен JSON и работает только со «своими» картами (README) |
| PCI DSS: маскирование PAN, шифрование, аудит | Синтетические данные; ТЗ-05 требует возвращать полный PAN |
| Бонусные функции (PIN, CVV, 3-D Secure, кэш карт, MTI 0200) | Не обязательны по ТЗ; проверяются, только если реализованы |
| Стек мониторинга как объект тестирования | Профиль `observability` выключен; в модулях 6–7 это инструмент сбора метрик |
| UX и кросс-браузерность дашборда | Проверяются только данные, real-time обновление и реконнект |
| Полное нагрузочное тестирование в CI | Раннеры GitHub не дают стабильных метрик; в CI только load-smoke |
| Внутреннее поведение PostgreSQL и RabbitMQ | Сторонние продукты; проверяется только интеграция СМП с ними |

## 4. Подход и принципы приоритизации

Подход риск-ориентированный: приоритет = вероятность дефекта × влияние на деньги и данные клиента.

| Приоритет | Области | Минимальный набор проверок |
|---|---|---|
| P1 — критичный | Решение авторизации, порядок проверок, коды отказа; резервирование и баланс; лимиты; уникальность RRN; нет `APPROVED` без записи в очередь | Все техники тест-дизайна, unit + API + интеграция + E2E |
| P2 — высокий | CRUD и генератор карт, soft delete; маршрутизация по BIN; валидация и rate limit Gateway; fallback Bin Lookup; идемпотентность Logger | Классы и границы, API + интеграция |
| P3 — средний | Симуляторы, уведомления, дашборд, поиск транзакций | Чек-листы, smoke, критический путь |

Принципы:

1. **Глубина следует за риском:** полный тест-дизайн — только для ядра, для периферии — чек-листы.
2. **Ожидаемый результат — из требований, а не из кода.** Приоритет источников: ТЗ → api-spec → OpenAPI. Противоречия фиксируются как вопросы аналитику, например `limit` по умолчанию 50 в ТЗ-05 и 10 в OpenAPI или отсутствие `EXPIRED` в PATCH по OpenAPI.
3. **Shift-left:** тест-дизайн выполняется до автотестов; классы и границы становятся параметрами unit-тестов модуля 3.
4. **Один невалидный класс — один тест.** В pairwise это обеспечивают ограничения модели и негативные значения PICT.
5. **Изоляция данных:** каждый денежный тест работает на своей карте и не зависит от случайных статусов генератора.
6. **Асинхронность проверяется опросом с таймаутом,** а не фиксированным `sleep`.
7. **Автоматизация регресса:** лёгкий CI на каждый push; smoke, E2E и load-smoke — вручную перед сдачей.
8. **Воспроизводимость дефектов:** зафиксированы commit, окружение, данные, шаги, ожидаемый и фактический результат.

Стратегия пересматривается при изменении ТЗ, API-контрактов, топологии сервисов или после выявления критического дефекта.
