# Тестовый план СМП

## 1. Область и подход

**Объект тестирования:** СМП из ветки `main` (11 сервисов + PostgreSQL + RabbitMQ), разворачивается командой `docker compose up -d`. Базис тестирования: `tz/02`–`tz/09`, `docs/api-spec.md`, `docs/api/openapi.yaml`, `docs/architecture.md`.

**Функции в области тестирования:**

| Функция | Сервис | Приоритет | Уровни |
|---|---|:---:|---|
| Решение авторизации, порядок проверок, коды отказа, лимиты | Authorization | P1 | Unit, API, интеграция, E2E |
| Резервирование средств, RRN, authCode | Authorization, CMS | P1 | API, интеграция, нагрузка |
| Создание карты: PAN по Луну, expiryDate, значения по умолчанию | Card Management | P1 | Unit, API |
| Список, получение, PATCH, мягкое удаление, генератор | Card Management | P2 | API, интеграция |
| Валидация, проксирование, rate limit, 503 при отказе downstream | Gateway | P2 | API |
| Маршрутизация по BIN, публикация в RabbitMQ, reversal | Switch | P1 | Интеграция, E2E |
| Журнал, поиск, статистика, WebSocket, идемпотентность | Transaction Logger | P2 | API, интеграция |
| Обогащение issuerId, fallback | Bin Lookup | P2 | API |
| Карточные события через outbox | Notification Service | P3 | Интеграция |
| Сценарии генерации транзакций | Terminal / Merchant Simulator | P3 | API |
| KPI, график, таблица, реконнект | Web Dashboard | P3 | E2E (ручной) |

Вне области — см. стратегию, раздел 3. Для ядра выполнен тест-дизайн (`test-design.md`, наборы в `pict/`), для остальных сервисов — чек-листы (`checklists.md`). Регресс: `ci.yml` на каждый push, `practice-run.yml` вручную.

**Последовательность работ:**

1. Проверить требования, API-контракты и трассировку.
2. Подготовить `.env`, поднять PostgreSQL, RabbitMQ и 11 сервисов.
3. Выполнить чек-лист дымового тестирования.
4. Создать независимые тестовые карты и состояния `limit_usage`.
5. Выполнить кейсы классов и границ, затем все строки обоих pairwise-наборов.
6. Выполнить критичные сочетания К-1…К-10.
7. Пройти чек-лист критического пути через Gateway.
8. Зафиксировать результаты и дефекты, провести регрессию исправлений.

**Тестовое окружение:**

| Компонент | Конфигурация |
|---|---|
| Стенд | Локально Docker Desktop (Windows 11); CI — GitHub Actions `ubuntu-latest` |
| Оркестрация | `docker compose` из репозитория, порты по `.env.example` |
| Хранилище | PostgreSQL 16 Alpine, только синтетические данные |
| Брокер | RabbitMQ 3.13 Management |
| Входная точка | Gateway `localhost:8080` |
| Ядро | Card Management `:8081`, Switch `:8082`, Authorization `:8083` |
| Диагностика | Логи контейнеров, health-check, RabbitMQ Management UI `:15672` |

**Тестовые данные:**

- собственные карты теста (`POST /api/cards` + `PATCH`) и пул генератора (BIN 400000–400004); каждый денежный кейс получает отдельную карту;
- состояния, недоступные через API (прошедший `expiryDate`, использование лимитов), задаются описанными фикстурами БД;
- отказы зависимостей — остановка контейнеров (`docker compose stop …`) или заглушка (ошибка `/reserve` в К-9).

## 2. Критерии входа и выхода

**Критерии входа (начало цикла тестирования):**

1. `docker compose up -d` поднимает все контейнеры; `scripts/smoke-test.sh` завершается строкой `ALL CHECKS PASSED`.
2. Требования ТЗ-04, ТЗ-05 и API-контракт доступны; тест-дизайн ядра выполнен, тест-кейсы трассированы на требования.
3. Справочник BIN (400000–400004) заполнен, сгенерировано не менее 20 тестовых карт.
4. Лёгкий CI (`ci.yml`) зелёный: сервисы собираются, линтеры проходят.

**Критерии выхода (завершение цикла):**

1. Выполнены все строки обоих pairwise-наборов и все вручную добавленные критичные сочетания.
2. Выполнено 100 % тест-кейсов приоритета P1, все P1 пройдены.
3. Выполнено не менее 95 % всех тест-кейсов, доля пройденных — не менее 90 %.
4. Нет открытых дефектов уровня Critical и High; для дефектов Medium есть решение (исправить или принять риск).
5. Покрытие требований ядра — 100 %: каждое требование R-AUTH-xx и R-CMS-xx из `test-design.md` имеет хотя бы один пройденный тест-кейс (раздел 5 «Прослеживаемость»).
6. Пройдены дымовое тестирование и критический путь «создание карты → авторизация → reserve → запись транзакции».
7. Для каждого падения заведён воспроизводимый дефект либо подтверждена причина в данных или окружении.
8. Результаты привязаны к commit и сохранены в Issue практики.
9. Покрытие строк бизнес-логики ядра unit-тестами — не менее 70 % (JaCoCo).
10. Нагрузочный smoke (500 транзакций локально): error rate < 1 %, p95 времени ответа `POST /api/transactions` < 500 мс.

**Критерии приостановки:**

- smoke-тест не проходит или не поднимается любой сервис ядра (Gateway, Switch, Authorization, CMS);
- найден блокирующий дефект: авторизация не возвращает решение или баланс меняется некорректно;
- более 30 % запланированных тест-кейсов заблокированы окружением или тестовыми данными.

**Критерии возобновления:** блокирующий дефект исправлен и подтверждён повторной проверкой; smoke-тест снова зелёный; окружение и тестовые данные восстановлены.

**Метрики:** покрытие требований тест-кейсами (%), доля выполненных и пройденных тест-кейсов (%), число открытых дефектов по severity, покрытие кода unit-тестами (%), p50/p95/p99 и error rate нагрузочного smoke.

## 4. Риски

| ID | Риск | Вероятность | Влияние | Меры снижения |
|---|---|:---:|:---:|---|
| Р-01 | Нестабильный стенд (13 контейнеров, нехватка памяти) даёт ложные падения | Средняя | Высокое | Ждать health-check, ограничить ресурсы контейнеров |
| Р-02 | Eventual consistency: запись в Logger запаздывает | Высокая | Среднее | Опрос с таймаутом вместо `sleep`, поиск по RRN |
| Р-03 | Противоречия ТЗ, api-spec, OpenAPI и кода (`limit` 50/10, порядок «лимиты → баланс») | Высокая | Высокое | Приоритет источников, вопросы аналитику |
| Р-04 | Гонка между проверкой баланса и `reserve`: двойное списание | Средняя | Высокое | Конкурентный тест К-6, сверка баланса и `limit_usage` |
| Р-05 | Зависимость от времени: конец месяца срока, смена суток и месяца, UTC и МСК | Средняя | Среднее | Явный `transmissionDateTime`, тесты на границах суток и месяца |
| Р-06 | Тесты влияют друг на друга через общие карты и usage | Высокая | Среднее | Своя карта на кейс, генератор только для нагрузки |
| Р-07 | Ограниченная квота GitHub Actions | Средняя | Низкое | Тяжёлые проверки — вручную перед сдачей |
| Р-08 | Один исполнитель и фиксированные дедлайны | Средняя | Среднее | Приоритизация P1 → P2 → P3, автоматизация регресса |
| Р-09 | Pairwise пропускает взаимодействие трёх и более факторов | Средняя | Высокое | Ручные критичные сочетания К-1…К-10 сверх 2-wise набора |
| Р-10 | Soft delete оставляет карту доступной операциям | Средняя | Высокое | Отдельная проверка GET, списка, reserve и авторизации после DELETE |
| Р-11 | Занятые порты или устаревшие образы контейнеров | Средняя | Высокое | `docker compose ps`, фиксация commit и образов, чистый перезапуск |
| Р-12 | Timeout и retry (Bin Lookup 3 с / 5 с, Switch — 3 попытки) удлиняют прогон | Средняя | Среднее | Управляемые заглушки, явные границы ожидания |

Главное допущение: ТЗ имеет приоритет над текущим поведением реализации. Если результат в ТЗ не определён, он помечается как вопрос к аналитику, а не автоматически как дефект.
