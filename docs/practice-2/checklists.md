# Чек-листы

Чек-лист перечисляет, что проверить, без конкретных данных и шагов. У каждого пункта есть ID и ссылка на требование; `[x]` — проверка пройдена.

## 1. Дымовое тестирование

Цель — за 5–10 минут убедиться, что сборка пригодна для тестирования. Перед началом: `docker compose up -d` для текущего commit, дождаться health-check, только синтетические данные. Большая часть пунктов автоматизирована в `scripts/smoke-test.sh`. Любой непройденный пункт приостанавливает тестирование.

**Инфраструктура**

- [ ] SM-01. Все контейнеры СМП в состоянии `Up (healthy)` по `docker compose ps`, циклических перезапусков нет (README, «Быстрый старт»)
- [ ] SM-02. PostgreSQL принимает подключения на порту 5432, миграции завершились успешно (`docs/architecture.md`)
- [ ] SM-03. RabbitMQ Management UI открывается на `:15672` (`smp`/`smp`); созданы exchange `smp.transactions`, `smp.card-events` и очереди `transaction-log`, `card-notifications` (ТЗ-03 §3, ТЗ-05)

**Health-check сервисов**

- [ ] SM-04. Gateway `GET /health` → 200, все зависимости в `services` со статусом `ok` (ТЗ-02 §1)
- [ ] SM-05. Card Management `GET /health` → 200, поле `cardsInDatabase` присутствует (ТЗ-05 §1)
- [ ] SM-06. Switch `GET /health` → 200 (ТЗ-03 §1)
- [ ] SM-07. Authorization `GET /health` → 200, `dependencies.cardManagement = ok` (ТЗ-04 §1)
- [ ] SM-08. Terminal Simulator `GET /health` → 200 (ТЗ-06 §1)
- [ ] SM-09. Merchant Simulator `GET /health` → 200 (ТЗ-07 §1)
- [ ] SM-10. Transaction Logger `GET /health` → 200 (ТЗ-08 §1)
- [ ] SM-11. Bin Lookup `GET /actuator/health` → 200
- [ ] SM-12. Notification Service `GET /actuator/health` → 200
- [ ] SM-13. Web Dashboard открывается на `:3000` без ошибок загрузки (ТЗ-09)

**Базовые функции**

- [ ] SM-14. Генерация карт `POST /api/cards/generate` через Gateway возвращает 201, `generated` равен запрошенному `count`, PAN проходят проверку Луна (ТЗ-05 §3)

- [ ] SM-21. После smoke в логах контейнеров нет необработанных исключений и непрерывных retry

## 2. Критический путь

Цель — проверить ключевые бизнес-сценарии процессинговой цепочки. Выполняется после дымового тестирования, перед сдачей и после изменений в ядре; порядок соответствует приоритету P1 → P3.

**Подготовка карты**

- [ ] CP-01. Создана ACTIVE-карта с зарегистрированным BIN и будущим `expiryDate`; PAN из 16 цифр проходит проверку Луна (ТЗ-05 §2, §4)
- [ ] CP-02. `dailyLimit`, `monthlyLimit` и `availableBalance` заведомо больше тестовой суммы; исходные баланс и `limit_usage` зафиксированы до операции

**Покупка с одобрением (сквозной сценарий)**

- [ ] CP-03. Покупка через `POST /api/transactions` (`mti = 0100`, уникальный STAN) возвращает `APPROVED`, `responseCode = 00` (ТЗ-04 §2, шаг 7)
- [ ] CP-04. В ответе `rrn` из 12 цифр, `authCode` из 6 символов A-Z0-9, `mti = 0110`, `stan` совпадает с запросом (ТЗ-04 §6, api-spec)
- [ ] CP-05. `availableBalance` уменьшился ровно на сумму транзакции, использованные дневной и месячный лимиты выросли на неё один раз (ТЗ-04 §3–4, ТЗ-05 §5)
- [ ] CP-06. RRN уникален: у двух транзакций, отправленных в одну секунду, разные RRN (ТЗ-04 §6)
- [ ] CP-07. Транзакция опубликована в RabbitMQ (exchange `smp.transactions`, очередь `transaction-log`) и сохранена в Logger со статусом `APPROVED` и `mti = 0100` в пределах согласованного времени ожидания (ТЗ-03 §3, ТЗ-08 §2)
- [ ] CP-08. Транзакция приходит в WebSocket `/ws/transactions` и появляется в таблице последних транзакций на дашборде (ТЗ-08 §6, ТЗ-09 §3)
- [ ] CP-09. `GET /api/dashboard/stats` учитывает транзакцию: растут `totalTransactions`, `approvedCount`, `totalAmount` (ТЗ-08 §4)

**Отказы авторизации**

- [ ] CP-10. Несуществующий PAN → `DECLINED`, `responseCode = 14` (ТЗ-04 §2, шаг 1)
- [ ] CP-11. Карта BLOCKED → `DECLINED`, `CARD_BLOCKED` (ТЗ-04 §2, шаг 2)
- [ ] CP-12. Карта INACTIVE → `DECLINED`, `CARD_INACTIVE` (ТЗ-04 §2, шаг 2)
- [ ] CP-13. Карта с истёкшим сроком → `DECLINED`, `responseCode = 54` (ТЗ-04 §2, шаг 3)
- [ ] CP-14. Превышение дневного лимита → `DECLINED`, `responseCode = 61` (ТЗ-04 §2, шаг 4)
- [ ] CP-15. Превышение месячного лимита → `DECLINED`, `responseCode = 61` (ТЗ-04 §2, шаг 5)
- [ ] CP-16. Недостаточно средств → `DECLINED`, `responseCode = 51` (ТЗ-04 §2, шаг 6)
- [ ] CP-17. При любом отказе баланс и использованные лимиты не изменились, транзакция сохранена в Logger со статусом `DECLINED` и причиной (ТЗ-04 §2, ТЗ-08 §2)

**Валидация и устойчивость**

- [ ] CP-18. Gateway отклоняет некорректный запрос (PAN не из 16 цифр, `amount ≤ 0`, нет обязательного поля) с HTTP 400 и `VALIDATION_ERROR` (ТЗ-02 §2)
- [ ] CP-19. Более 100 запросов в секунду на `/api/transactions` → HTTP 429 `RATE_LIMIT_EXCEEDED` (ТЗ-02 §4)
- [ ] CP-20. PAN с BIN вне таблицы маршрутизации → Switch возвращает `DECLINED`, `responseCode = 14` (ТЗ-03 §4)
- [ ] CP-21. Authorization недоступен → Switch делает 3 попытки, затем `DECLINED`, `responseCode = 05` (ТЗ-03 §4)
- [ ] CP-22. Card Management недоступен → Authorization возвращает `DECLINED`, `responseCode = 05`, `ISSUER_TIMEOUT`; баланс и `limit_usage` не изменились (ТЗ-04 §5)
- [ ] CP-23. Bin Lookup недоступен → авторизация завершается решением по общим правилам (fallback, ТЗ-04 §2)
- [ ] CP-24. RabbitMQ недоступен при одобренной транзакции → reversal (`mti = 0400`), баланс восстановлен один раз, клиент получает `DECLINED`, `responseCode = 96` (ТЗ-03 §4)
- [ ] CP-25. Downstream-сервис недоступен → Gateway возвращает HTTP 503 `SERVICE_UNAVAILABLE` (ТЗ-02 §5)
- [ ] CP-26. Повторная доставка транзакции с тем же `id` не создаёт дубликат в Logger (ТЗ-08 §2)

**Управление картами**

- [ ] CP-27. Создание карты → 201, PAN проходит проверку Луна, `status = ACTIVE`, `expiryDate` = текущая дата + 3 года (ТЗ-05 §2)
- [ ] CP-28. Изменение статуса карты на BLOCKED через `PATCH` сразу приводит к отказу авторизации (ТЗ-05 §2, ТЗ-04 §2)
- [ ] CP-29. Повтор reserve с тем же RRN не уменьшает баланс второй раз (ТЗ-05 §5, OpenAPI ReserveRequest)
- [ ] CP-30. Удалённая карта (`DELETE`) не возвращается в `GET /api/cards/{pan}` и списке, не участвует в reserve и авторизации (ТЗ-05 §2)
- [ ] CP-31. Создание, изменение и удаление карты порождают события в Notification Service (`GET /api/notifications`) через outbox; в `card-notifications-dlq` нет неожиданных сообщений (ТЗ-05, раздел «Outbox»)

**Симуляторы и дашборд**

- [ ] CP-32. Terminal Simulator, сценарий `declines_test`: около 20 % каждого типа отказов (14, CARD_BLOCKED, 51, 61) и 20 % одобрений (ТЗ-06 §3)
- [ ] CP-33. Merchant Simulator по каждому сценарию (`grocery`, `electronics`, `restaurant`, `travel`) отправляет транзакции с MCC сценария, `acquiringFee` рассчитан (ТЗ-07 §5–6)
- [ ] CP-34. Дашборд: KPI-карточки, график и круговая диаграмма обновляются в реальном времени; после обрыва WebSocket — автоматический реконнект и смена индикатора (ТЗ-09 §2, §5)
- [ ] CP-35. Поиск транзакций `GET /api/transactions/search` с комбинацией фильтров (`pan` + `status` + период) возвращает пересечение условий (ТЗ-08 §3)
